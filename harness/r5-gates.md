## 통과 조건 (기계가 셈)
| 게이트 | 구간 | 통과 조건 (전부 만족) |
|---|---|---|
| G1 | S1→S2 | 경쟁사 3개 이상, 화면당 레퍼런스 5개 이상, 모든 레퍼런스에 uibowl URL과 ID |
| G2 | S2→S3 | 반영 포인트 9개 이상 (화면당 3개 이상), 각 항목에 S1 레퍼런스 ID 근거 1개 이상 |
| G3 | S3→S4 | 화면 3개 존재, 화면마다 필수 섹션(구성 요소, 상태, 상호작용) 존재, V1·V2 요구 명시 (내 자산 화면에 공개 범위 3옵션, 금지 항목 안내, 확인 체크박스), MVP 제외 표현 0개 (허들링 픽 노출, 구매, 피드백, 판매 중, 판매 중지) |

| G6 | S6→S7 | 컴포넌트 7개 존재, 변수 값이 rules.json 집합 안, D02·D04·D07·D09 위반 0 |
| G7 | S7→S8 | 완성본 프레임 3개, 화면의 상태 배지가 status_badges 스타일과 일치 |
| G8 | 종료 | D01~D12 위반 0, V1·V2 위반 0, 배지 불일치 0 |

## V1·V2 (어기면 안 되는 것)
- 검사 위치: G3 (설계 문서), G4 (키스크린), G8 (최종)
- 하나라도 위반이면 통과 불가. 사람 승인으로도 넘길 수 없음
- 검사 항목 원본: rules.json `violations`

## 사람 승인 (1곳: S5)
- 사람이 "확정" 입력 → output/run/s5-approval.md에 확정 일시, 확정 프레임 ID, 메모 기록
- G5 통과 조건: 확정 프레임 ID가 S4 프레임 ID의 부분집합
- 안 방식(variants≥2)이면 추가로: 대상 화면마다 확정한 안이 정확히 하나. 사람은 화면마다 안 하나를 고른다 (예: 홈 B, 스킬 A, 내 자산 C). 같은 안의 상태 프레임(@seller, @non-seller)은 함께 확정한다
- 승인 없이 S6 진입 불가
- 사람이 "수정 요청" 입력 → S4로 복귀, S5 이후 산출물 전부 pending

## 실패 시 복귀
- 같은 단계 재작업, 최대 3회. 3회 연속 실패 시 정지하고 위반 목록을 사람에게 보고 (승인 아님)
- G8 실패: 위반 노드가 컴포넌트 내부면 S6으로, 화면 수준이면 S7로 복귀
- 앞 단계 산출물이 바뀌면 뒤 단계는 output/run/state.json에서 pending으로 되돌려 재실행
- 대상 화면은 실행 시작 입력값(state.json input.screens, 기본 3개)을 따른다. 화면 수 기준(G1~G3, G4 최소 개수, G7 필수 프레임)은 대상 화면에 비례해 적용한다 (화면 → 프레임 매핑: rules.json gates.screen_frames)
- 게이트 수치 원본: rules.json `gates` (이 표의 숫자는 설명용, 어긋나면 rules.json 우선)
